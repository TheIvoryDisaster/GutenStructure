# Owner-author approval policy (staged, not enforced)

An applicable code owner's authorship authorizes their paths. On beta/main, other paths require an applicable owner's current approval. Release additionally requires at least one eligible non-author approval on the current head. A non-author code owner's approval can satisfy both conditions. Every changed path must be authorized; rename source and destination are checked. Outstanding changes-requested reviews block the preview.

This intentionally replaces the older two-external-reviewer policy only after validation and a separate enforcement rollout. Native GitHub does not accept self-approvals. No current protections or release gate were changed by this implementation.

## Preview

Run `OWNER_POLICY_TOKEN=... python -m scripts.owner_approval Meitou-Modding-Ecosystem/RivalryCore 71` with a safely supplied environment secret, never a literal token in shell history. The script only reads API data. Use repository metadata/contents/pull requests read access, collaborator permission read access, and organization Members read for teams. It verifies organization ID 357134506, public visibility, complete pagination, the target-branch CODEOWNERS at an immutable base SHA, current reviews, writer eligibility, and stable base/head before reporting. It never executes PR code or writes a check. Unsupported CODEOWNERS syntax fails closed; supported pattern matching needs comparison against GitHub before enforcement. Native CODEOWNERS errors and team visibility/explicit repository assignment also need validation during rollout.

## Service implementation and remaining activation steps

The staged implementation now includes `scripts/owner_check_service.py` and the Azure Functions adapter under `services/owner-check/`. Signed GitHub webhooks are durably queued; queue processing evaluates live API data and creates **Meitou owner authorization** through a dedicated App installation. A five-minute reconciliation scan covers current/future public repositories in that installation. It never runs PR code or accepts organization workflow credentials. Current-head reviews are required; changes requested by an eligible writer block. Team owners must be visible and explicitly assigned repository write access. Unsupported ownership syntax or API errors fail closed.

Because GitHub checks attach to a SHA rather than a PR, every open protected PR sharing that head must pass; a beta success must never override a release failure at the same SHA. Complete empty/history-only diffs need no path-owner approval, but release still requires an independent current-head review; the API inventory count must match. Multiple instances/event delivery can race; webhook and membership tests, serialized processing and out-of-order delivery testing remain activation prerequisites. As with other asynchronous review checks, review/base/team changes have an event-processing window; a timer is reconciliation, not instant authorization revocation. Existing native requirements remain active during this pilot.

Apply package/dependency security review before deployment; unit tests do not establish hosting or dependency compatibility.

Test owner/non-owner authors, mixed ownership, team updates, independent release reviewer, revoked/stale reviews, base changes, forks and identical heads across PRs. 7. Only after the pilot, wire `scripts/custom_owner_policy.py` into central reconciliation using the verified App ID. The builder preserves mandatory CI, requires PRs with zero native reviewers on beta/main and one on release, and binds the custom required check to the dedicated App, with no bypass. Remove superseded owner-review rules (including broad Actions/team bypass) while preserving independent rules. The existing release gate still requires the older policy: update/test/promote it and both trusted helper pins as one coordinated rollout, then apply/read back every repo. This PR intentionally does not weaken scheduled reconciliation or the release gate before the App is functional.

**Current evidence:** evaluator/service unit tests pass locally; no App exists for this task yet, no webhook was deployed, no App-authenticated check was posted, and no repository protections were replaced. App registration/installation and secure credential configuration require the owner's account-side action. The previous draft was a policy preview, not an already deployed service.
