# Owner-author approval policy (staged, not enforced)

An applicable code owner's authorship authorizes their paths. On beta/main, other paths require an applicable owner's current approval. Release additionally requires at least one eligible non-author approval on the current head. A non-author code owner's approval can satisfy both conditions. Every changed path must be authorized; rename source and destination are checked. Outstanding changes-requested reviews block the preview.

This intentionally replaces the older two-external-reviewer policy only after validation and a separate enforcement rollout. Native GitHub does not accept self-approvals. No current protections or release gate were changed by this implementation.

## Preview

Run `OWNER_POLICY_TOKEN=... python -m scripts.owner_approval Meitou-Modding-Ecosystem/MeitouMods 71` with a safely supplied environment secret, never a literal token in shell history. The script only reads API data. Use repository metadata/contents/pull requests read access, collaborator permission read access, and organization Members read for teams. It verifies organization ID 357134506, public visibility, complete pagination, the target-branch CODEOWNERS at an immutable base SHA, current reviews, writer eligibility, and stable base/head before reporting. It never executes PR code or writes a check. Unsupported CODEOWNERS syntax fails closed; supported pattern matching needs comparison against GitHub before enforcement. Native CODEOWNERS errors and team visibility/explicit repository assignment also need validation during rollout.

## Trusted enforcement rollout

1. Create a dedicated GitHub App controlled by TheIvoryDisaster. Install it only in Meitou-Modding-Ecosystem. Permissions: Metadata read, Contents read, Pull requests read, Checks read/write, and organization Members read. Repository administration read may be needed to validate collaborator permissions. Do not give it Contents write or repository Administration write. Verify exact endpoint permissions in a read-only pilot before enabling check writes.
2. Keep the App private key in GutenStructure's protected environment, never in organization repositories or reusable caller secrets. Use short-lived installation tokens restricted to each evaluated repository. Bind the required check to this App's integration ID so contributors cannot forge it with Actions' GITHUB_TOKEN. The current administration token is not a substitute for a distinct trusted check identity.
3. Build a trusted service/webhook receiver that validates GitHub webhook signatures and installation/repository IDs. React to PR opens/reopens, synchronization, base changes, reviews/dismissals, and ownership/team permission changes. Recompute periodically too. Execute only released GutenStructure code; never checkout/run PR content. Mark checks pending during reevaluation, and handle head/base changes and review revocation races. This preview alone is not a production webhook service.
4. Test owner/non-owner authors, mixed ownership, team membership, renamed paths, dismissed/stale reviews, changes requested, fork PRs, tampered workflow/check names, and base changes. Use a beta pilot with existing protections intact; compare CODEOWNERS results against GitHub. Test external review permissions and event delivery in hosted runs.
5. After owner feedback, update central branch reconciliation to PR-required, zero native owner reviews for beta/main and one native external review for release, plus the App-bound required check and all existing CI. Remove the broad super-maintainers review bypass. Retain force-push/deletion protection, stale-review dismissal and no release bypass. Last-push approval needs deliberate review because it can demand an additional reviewer beyond the requested policy.
6. Update release_gate.py and its tests to require this new App-bound enforced policy; promote both gate and packaging helper pins together. Existing gate expects the previous policy and must not be relaxed in isolation. Apply/read back all repositories, then test a real release. Keep the old policy until all new checks are working and fail-closed.

GutenStructure remains the separate personal exception (PR plus CI, zero reviewers). Ordinary organization branches remain unprotected. New repositories must receive the App installation and required check before this policy can apply to them.
